## 1. 한눈에 보기

테스트는 세 계층으로 나뉨. 아래로 갈수록 느리지만 실제 사용 환경에 가까움.

| 계층             | 도구                                 | 위치                            | 검증 대상                                      | 실행 시간 | 규모              |
| ---------------- | ------------------------------------ | ------------------------------- | ---------------------------------------------- | --------- | ----------------- |
| BE API·단위      | Jest + Supertest                     | `be/tests/api`, `be/tests/unit` | 라우트·인증·검증·권한·상태 분기 (DB는 가짜)    | 약 2초    | 14개 파일 · 253개 |
| BE 통합          | Jest + **실제 PostgreSQL**           | `be/tests/integration`          | 배치 SQL, 제출→승인→메일 흐름, 시간대          | 약 2초    | 2개 파일 · 26개   |
| FE 단위·컴포넌트 | Vitest + React Testing Library + MSW | `fe/src/**/*.test.ts(x)`        | 화면 동작, API 연동, 401 처리 (API는 가짜)     | 약 2초    | 14개 파일 · 173개 |
| 브라우저 E2E     | Playwright (Chromium)                | `fe/e2e`                        | 캡틴·크루 시나리오 전체 (실제 DB·BE·빌드된 FE) | 약 30초   | 3개 파일 · 24개   |

### 실행 명령

| 하고 싶은 것                 | 명령                                                            | 위치  |
| ---------------------------- | --------------------------------------------------------------- | ----- |
| BE 전체 (DB 없이, CI와 동일) | `npm test`                                                      | `be/` |
| BE 파일 하나                 | `npx jest tests/api/review.test.js`                             | `be/` |

## 3. BE 테스트 (Jest + Supertest)

### 3.1 구조

```
be/
├── jest.config.js              # tests/**/*.test.js 실행, setupFiles로 env.js 적용
└── tests/
    ├── api/                    # 실제 Express 앱에 HTTP 요청 (DB는 가짜)
    │   ├── helpers/
    │   │   ├── env.js          # 테스트용 환경변수 고정 + morgan 로그 끔
    │   │   ├── fakeDb.js       # models 대체 객체 (모델별 jest.fn)
    │   │   └── token.js        # bearer(), expiredBearer() JWT 생성
    │   ├── auth.test.js, meetup.test.js, logbook.test.js, review.test.js ...
    │   └── requirements-gaps.test.js   # 미구현 요구사항 (test.todo)
    ├── unit/                   # 서비스 로직·미들웨어 단위 검증
    └── integration/            # 실제 PostgreSQL (TEST_DATABASE_URL 없으면 건너뜀)
```

### 3.2 동작 원리

- **DB는 가짜**: `jest.mock('../../src/models', () => require('./helpers/fakeDb'))` 한 줄로 모든 모듈의 `models`가 `fakeDb`로 바뀜. 각 테스트에서 `db.Meetup.findByPk.mockResolvedValue(...)`처럼 DB 응답을 정함.
- **나머지는 실제 코드**: 라우트, 인증 미들웨어, 검증, 서비스 분기, 에러 핸들러는 모두 진짜로 실행됨.
- **환경변수 고정**: `env.js`가 `JWT_SECRET=test-secret`, `BATCH_API_KEY=test-batch-key`, `SALT_ROUNDS=4`를 먼저 설정함. `be/.env`는 이미 설정된 값을 덮어쓰지 못하므로 로컬 `.env`와 무관하게 같은 결과가 나옴.
- **트랜잭션**: `db.reset()`이 `sequelize.transaction`을 "콜백 즉시 실행"으로 되돌림. 매 테스트 `beforeEach(() => db.reset())` 필수.
- **메일**: `jest.mock('../../src/common/services/mailer.service')`로 대체해 `sendMail` 호출만 검증함. 실제 메일은 보내지 않음.

### 3.3 API 테스트 작성 예시

새 API를 만들면 `be/tests/api/<모듈>.test.js`에 아래 형태로 추가함.

```js
// REQ-REV-001 모임 후기 관리
jest.mock('../../src/models', () => require('./helpers/fakeDb'));

const request = require('supertest');
const db = require('./helpers/fakeDb');
const app = require('../../src/app');
const { bearer } = require('./helpers/token');

beforeEach(() => db.reset());

describe('PATCH /review/meetups/:id/me 후기 수정 (REQ-REV-001)', () => {
  test('토큰이 없으면 401', async () => {
    const res = await request(app)
      .patch('/review/meetups/1/me')
      .send({ content: '수정', rating: 4 });
    expect(res.status).toBe(401);
  });

  test('본인 후기를 수정함', async () => {
    // given: DB가 돌려줄 값을 정함
    db.Meetup.findByPk.mockResolvedValue({
      meetup_id: '1',
      leader_id: 'leader01',
      status: 'COMPLETED',
    });
    db.Apply.findOne.mockResolvedValue({ apply_id: 10 });
    const review = { update: jest.fn(async (v) => v) };
    db.Review.findOne.mockResolvedValue(review);

    // when: 실제 HTTP 요청
    const res = await request(app)
      .patch('/review/meetups/1/me')
      .set('Authorization', bearer('crew01'))
      .send({ content: '수정', rating: 4 });

    // then: 응답 + DB에 무엇을 쓰려 했는지
    expect(res.status).toBe(200);
    expect(review.update).toHaveBeenCalledWith(
      expect.objectContaining({ rating: 4 }),
      expect.anything(),
    );
  });
});
```

**API마다 최소한 확인할 것**

| 구분      | 예                                                                   |
| --------- | -------------------------------------------------------------------- |
| 인증      | 토큰 없음 401, 만료·위조 401                                         |
| 권한      | 캡틴 전용 API에 크루 403, 다른 모임 사람 403                         |
| 입력 검증 | 잘못된 id(`abc`) 400, 필수값 누락 400, 경계값 (인원 3명·4명·8명·9명) |
| 상태      | 없는 리소스 404, 상태 충돌 409 (이미 신청, 종료 전 후기 등)          |
| 성공      | 응답 본문 + DB에 쓰는 값(`create`/`update` 인자)                     |
| 보안      | 응답에 비밀번호·내부 오류 문자열이 없는지                            |

### 3.4 통합 테스트 (실제 PostgreSQL)

목(mock)으로는 Sequelize의 `include`·`where`나 원시 SQL이 실제 DB에서 맞게 동작하는지 증명할 수 없음. 배치 SQL, 여러 테이블 조인, 날짜 계산을 바꿨다면 통합 테스트를 실행함.

```bash
# 1) 일회용 PostgreSQL 실행 (운영 DB와 무관)
initdb -D /tmp/sharestory-pg -A trust -U postgres --no-locale -E UTF8
pg_ctl -D /tmp/sharestory-pg -o "-p 54329 -c listen_addresses=127.0.0.1" -l /tmp/sharestory-pg.log start

# 2) 실행 (테스트가 DB를 새로 만들고 끝나면 삭제함)
cd be
TEST_DATABASE_URL=postgres://postgres@127.0.0.1:54329/postgres npm run test:db

# 3) 정리
pg_ctl -D /tmp/sharestory-pg stop && rm -rf /tmp/sharestory-pg /tmp/sharestory-pg.log
```

- `TEST_DATABASE_URL`에는 **반드시 로컬 일회용 DB**를 지정함. 테스트가 데이터베이스를 만들고 지움.
- 배치 테스트는 DB 전체를 대상으로 동작하므로, 메일 배치 테스트처럼 다른 테스트 데이터가 섞이면 안 되는 블록은 `beforeEach`에서 `TRUNCATE`함 (`batch-sql.test.js` 참고).
- **서버 시간대 재현**: Azure App Service는 UTC로 동작함. Jest 안에서는 `process.env.TZ`를 바꿔도 적용되지 않으므로, 시간대 검증은 `TZ=UTC`로 별도 프로세스를 띄워 확인함 (`batch-sql.test.js`의 `closeInProcess` 참고).

## 4. FE 단위·컴포넌트 테스트 (Vitest + RTL + MSW)

### 4.1 구조

```
fe/
├── vite.config.ts          # test: jsdom, setupFiles, VITE_API_BASE_URL=http://localhost:3000
└── src/
    ├── test/
    │   ├── setup.ts        # MSW 서버 시작, 매 테스트 후 cleanup·핸들러 초기화·localStorage 비움
    │   ├── server.ts       # MSW 서버 (기본 핸들러 없음), API 주소 상수
    │   └── render.tsx      # renderAt(), signIn() 헬퍼
    └── features/**/xxx.test.ts(x)   # 테스트 대상 파일 옆에 둠
```

### 4.2 규칙

- **API는 MSW로 대체**: 각 테스트가 `server.use(http.get(...))`로 필요한 응답만 정함. 정하지 않은 요청이 나가면 **테스트가 실패함** (`onUnhandledRequest: 'error'`). 실제 네트워크로 새는 요청을 막기 위한 설정임.
- **로그인 상태**: `signIn('crew01')`이 localStorage에 토큰(`test-token`)과 회원 정보를 넣음. `AuthProvider`가 이를 읽음.
- **라우터·인증 포함 렌더링**: `renderAt(<컴포넌트 />, { path: '/meetups/:meetupId', route: '/meetups/1' })`. `route`에 `{ pathname, state }`를 주면 `location.state`도 재현됨. 다른 경로로 이동하면 `data-testid="location"`에 현재 경로가 표시됨.
- **사용자 동작**: `fireEvent` 대신 `userEvent.setup()`을 사용함 (실제 입력 순서와 포커스를 흉내 냄).
- **셀렉터**: `getByRole` → `getByLabelText` → `getByPlaceholderText` → `getByText` 순으로 사용함. CSS 클래스는 CSS Modules가 해시하므로 사용하지 않음.

### 4.3 작성 예시

> 아래는 구조를 보여주는 축약 예시임. 모임 상세 응답 데이터는 `MeetupDetailView.test.tsx`의 `detail()` 함수를 그대로 사용함.

```tsx
import { describe, expect, it } from 'vitest';
import { screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { http, HttpResponse } from 'msw';
import { server, API } from '../../../../test/server';
import { renderAt, signIn } from '../../../../test/render';
import MeetupDetailView from './MeetupDetailView';

describe('MeetupDetailView 참여 신청 (REQ-PAY-001)', () => {
  it('정원 초과면 서버 메시지를 보여주고 버튼을 다시 활성화함', async () => {
    signIn('crew01');
    server.use(
      http.get(`${API}/meetup/1`, () =>
        HttpResponse.json({ success: true, document: /* 상세 응답 */ {} }),
      ),
      http.post(`${API}/meetup/1/apply`, () =>
        HttpResponse.json(
          { success: false, message: '모집 인원이 마감되었습니다.' },
          { status: 409 },
        ),
      ),
    );
    renderAt(<MeetupDetailView />, { path: '/meetups/:meetupId', route: '/meetups/1' });

    await userEvent.setup().click(await screen.findByRole('button', { name: '항해 참여하기' }));

    expect(await screen.findByText('모집 인원이 마감되었습니다.')).toBeInTheDocument();
    expect(screen.getByRole('button', { name: '항해 참여하기' })).toBeEnabled();
  });
});
```

**화면마다 최소한 확인할 것**: 로딩 → 성공 표시 → 빈 상태 → 서버 오류 메시지 → 요청 중 버튼 비활성화(중복 제출 방지) → 401이면 로그아웃·로그인 화면 이동.

### 4.4 알아둘 제약

- **파일 업로드**: jsdom의 `File`을 Node fetch가 직렬화하면 파일명·내용이 사라짐. 업로드 테스트는 필드명(`name="image"`)과 MIME만 검증함. 실제 업로드는 BE 테스트와 배포 후 확인으로 보완함.
- **API 주소**: 테스트에서는 `VITE_API_BASE_URL`이 `http://localhost:3000`으로 고정됨. 핸들러 주소는 `API` 상수를 사용함.

## 5. 브라우저 E2E (Playwright)

### 5.1 실행 구조

`npm run test:e2e` 한 번으로 아래 세 서버가 자동으로 뜨고, 테스트가 끝나면 모두 종료됨.

| 서버       | 스크립트            | 주소              | 내용                                                       |
| ---------- | ------------------- | ----------------- | ---------------------------------------------------------- |
| PostgreSQL | `e2e/scripts/db.sh` | `127.0.0.1:54330` | 실행할 때마다 새 데이터 디렉터리 생성 (`e2e/.pgdata`), UTC |
| BE         | `e2e/scripts/be.sh` | `127.0.0.1:3100`  | 실제 `src/server.js`. Azure·SMTP 설정은 빈 값으로 막음     |
| FE         | `e2e/scripts/fe.sh` | `127.0.0.1:4173`  | **프로덕션 빌드**(`.e2e-dist`) 후 `vite preview`           |

- 운영 DB, Azure Blob, SMTP에 접근하지 않음.
- 하나의 DB를 공유하므로 `workers: 1`로 순차 실행함. 대신 각 테스트가 **고유한 계정·모임을 새로 만들어** 서로 영향을 주지 않음.
- 실패하면 `fe/e2e/.artifacts/`에 스크린샷·트레이스가 남음. 트레이스는 `npx playwright show-trace <경로>/trace.zip`으로 단계별 화면을 볼 수 있음.

### 5.2 시나리오 구성

| 파일              | 테스트 수 | 내용                                                                                                                                                               |
| ----------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `smoke.spec.ts`   | 3         | favicon·로고 로딩, 홈 렌더링, 콘솔 오류 없음                                                                                                                       |
| `captain.spec.ts` | 9         | C1 가입·로그인 → C2 모임 개설 → C3 상세 → C4 수정·권한 → C5 크루 목록 → C6 숙제 승인·취소 → C7 종료 후 후기 조회 (`describe.serial`: 앞 단계의 모임을 이어서 사용) |
| `crew.spec.ts`    | 12        | K1 비로그인 신청 흐름, K2 가입 검증, K3 신청 오류, K4 마이페이지, K5 로그북(작성·모아보기·권한), K6 후기, K7 정보 수정·탈퇴, K8 토큰 만료 (각 테스트가 독립)       |

각 테스트의 사전 조건·수행 절차·기대 결과는 5.7 테스트 케이스 명세에 정리함.

### 5.3 헬퍼

**사전 조건은 API로 빠르게 만들고, 검증하려는 동작만 화면으로 함.**

| 헬퍼 (`e2e/helpers/api.ts`)                                   | 용도                                                               |
| ------------------------------------------------------------- | ------------------------------------------------------------------ |
| `createAccount(request, 이름)`                                | 가입 + 로그인 → `{ userId, token, user }`                          |
| `createMeetup(request, 캡틴, { maxCapacity })`                | 4회차 모임 개설 (모든 회차 미래 날짜) → `{ meetupId, sessionIds }` |
| `apply(request, 크루, meetupId)`                              | 참여 신청                                                          |
| `submitLogbook(...)`, `approveLogbook(...)`, `myLogbook(...)` | 로그북 제출·승인·조회                                              |
| `completeMeetup(meetupId)`                                    | 모임을 종료 상태로 변경 (후기 테스트용, 임시 DB에 직접 반영)       |
| `sql(query)`                                                  | 임시 DB에 SQL 실행 (API로 만들 수 없는 상태용)                     |
| `signInAs(page, 계정)`                                        | 화면 로그인 없이 로그인 상태로 시작                                |
| `uniqueId()`, `dateAfter(일)`                                 | 겹치지 않는 아이디, 미래 날짜                                      |

| 헬퍼 (`e2e/helpers/ui.ts`)        | 용도                                |
| --------------------------------- | ----------------------------------- |
| `signUpViaUi(page, 아이디, 이름)` | 가입 화면을 실제로 채워 가입        |
| `loginViaUi(page, 아이디)`        | 로그인 화면에서 로그인              |
| `fillMeetupForm(page, 값)`        | 모임 개설 화면 입력 (회차 4개 포함) |

### 5.4 작성 예시

```ts
import { expect, test } from '@playwright/test';
import { apply, createAccount, createMeetup, signInAs } from './helpers/api';

test('K4 신청한 모임이 마이페이지 크루 탭에 보임', async ({ page, request }) => {
  // 준비: API로 빠르게
  const captain = await createAccount(request, '캡틴');
  const crew = await createAccount(request, '크루');
  const m = await createMeetup(request, captain);
  await apply(request, crew, m.meetupId);

  // 검증: 실제 화면으로
  await signInAs(page, crew);
  await page.goto('/mypage/journal');
  await expect(page.getByText(m.title)).toBeVisible();
});
```

### 5.5 셀렉터 규칙

- `getByRole('button', { name: '…' })` → `getByLabel` → `getByPlaceholder` → `getByText` 순으로 사용함.
- 섹션 제목과 입력창 이름이 같으면 "strict mode violation"이 남. `{ exact: true }`, 역할(`getByRole('textbox', …)`), 플레이스홀더로 좁힘.
- 레이블에 "필수"·안내 문구가 함께 들어간 입력창은 정확 일치가 안 됨. 폼 범위로 좁힌 뒤 순서로 찾음 (`crew.spec.ts`의 비밀번호 변경 참고).
- `<details>`처럼 열고 닫는 요소는 이미 열려 있는지 확인 후 클릭함 (다시 누르면 닫힘).
- `window.confirm`은 `page.once('dialog', (d) => d.accept())`를 클릭 **전에** 등록함.
- 화면에 없어야 하는 요소는 `toHaveCount(0)`으로 확인함 (예: 마감된 모임의 "항해 참여하기", 읽기 전용 화면의 입력창).

모든 명령은 `fe/`에서 실행함.

**1) 기본 실행**

| 목적                    | 명령                                   | 비고                                            |
| ----------------------- | -------------------------------------- | ----------------------------------------------- |
| 전체 실행               | `npm run test:e2e`                     | 서버 3개 자동 실행·종료, 약 30초                |
| 파일 하나               | `npx playwright test e2e/crew.spec.ts` |                                                 |
| 이름으로 필터           | `npx playwright test -g "K5"`          | 테스트 이름(또는 describe 이름)에 포함된 문자열 |

**2) 실패 원인 찾기**

| 도구          | 명령                                                                  | 언제 쓰나                                                                 |

**3) 셀렉터 찾기 (codegen)**

테스트를 새로 쓸 때 화면을 직접 클릭하면 Playwright가 셀렉터를 제안해 줌. codegen은 테스트 서버를 자동으로 띄우지 않으므로 서버를 직접 실행함.

```bash
# 터미널 1~3: 서버를 직접 실행 (각각 따로 띄움)
bash e2e/scripts/db.sh
bash e2e/scripts/be.sh
bash e2e/scripts/fe.sh

# 터미널 4: 화면을 조작하며 셀렉터 확인
npx playwright codegen http://127.0.0.1:4173
```

- 제안된 셀렉터 중 `getByRole`·`getByLabel` 형태를 골라 씀. CSS 클래스 기반 셀렉터는 쓰지 않음 (CSS Modules 해시가 빌드마다 바뀜).
- 작업이 끝나면 직접 띄운 서버를 반드시 종료함 (Ctrl+C). 켜 둔 채 `npm run test:e2e`를 실행하면 포트 충돌로 시작하지 않음.

### 5.8 새 시나리오 추가 절차

1. **케이스 정의**: 5.7 표 형식으로 사전 조건·수행 절차·기대 결과를 먼저 적음. 요구사항 ID를 붙임.
2. **위치 결정**: 캡틴 관점이면 `captain.spec.ts`, 크루 관점이면 `crew.spec.ts`. 이전 단계 결과에 의존하지 않는 독립 테스트로 작성함 (`captain.spec.ts`의 serial 흐름에 끼워 넣는 것은 그 흐름의 다음 단계일 때만).
3. **준비는 API로**: `createAccount`·`createMeetup`·`apply` 등으로 사전 조건을 만듦. API로 만들 수 없는 상태(종료된 모임 등)만 `sql()`·`completeMeetup()`을 사용함. 필요한 헬퍼가 없으면 `helpers/api.ts`에 추가함.
4. **검증은 화면으로**: 사용자가 보는 문구·버튼 상태·이동 경로를 확인함. 서버에 정말 저장됐는지는 API(`myLogbook` 등)로 함께 확인함.
5. **셀렉터**: `--ui` 또는 codegen으로 확인하고 5.5 규칙을 따름.
6. **안정성 확인**: 해당 테스트를 3회 이상 연속 실행해 모두 통과하는지 확인함 (`npx playwright test -g "K9" --repeat-each=3`).
7. **변조 검증**: 대상 기능을 한 줄 망가뜨려 테스트가 실패하는지 확인 후 원복함 (6.4 참고).
8. **문서 반영**: 이 문서 5.7과 요구사항 정의서 10장 매핑을 갱신함.

## 6. 작성 원칙

### 6.1 무엇을 바꾸면 어떤 테스트를 쓰나

| 변경                           | BE API·단위              | BE 통합  | FE 단위        | E2E      |
| ------------------------------ | ------------------------ | -------- | -------------- | -------- |
| 새 API·검증 규칙·권한          | **필수**                 |          |                |          |
| 배치 SQL·조인 쿼리·날짜 계산   | 필수                     | **필수** |                |          |
| 메일 발송 대상·내용            | **필수** (`sendMail` 목) | 권장     |                |          |
| 화면 입력 검증·표시 로직       |                          |          | **필수**       |          |
| API 호출 방식·오류 처리        |                          |          | **필수** (MSW) |          |
| 여러 화면을 거치는 사용자 흐름 |                          |          |                | **필수** |
| 라우팅·로그인 리다이렉트       |                          |          | 필수           | 권장     |

### 6.2 이름과 요구사항 표기

- 테스트 이름은 **한국어로 기대 동작**을 적음. 예: `'정원이 이미 찼으면 409'`, `'승인된 신청자에게만 발송함'`.
- `describe`에 요구사항 ID를 붙임. 예: `describe('POST /meetup 모임 등록 (REQ-GRP-001)', …)`. 요구사항 정의서 10장의 매핑에 반영함.
- 주석은 간결체(`~함`, `~임`, 명사형)로 씀.

### 6.3 알려진 결함과 미구현 항목

| 상황                                       | 사용                                                      | 효과                                                                                         |
| ------------------------------------------ | --------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 요구사항대로 동작하지 않는 **알려진 결함** | `test.failing('요구사항대로의 기대 동작', …)` + 원인 주석 | 결함이 있는 동안은 통과로 표시됨. 고치면 "Failing test passed" 오류로 알려줌 → `test`로 바꿈 |
| 아직 구현하지 않은 요구사항                | `test.todo('REQ-… 설명')` (`requirements-gaps.test.js`)   | 출력에 todo로 표시됨. 구현하면 실제 테스트로 바꾸고 목록에서 뺌                              |

> `test.failing`은 **엉뚱한 이유로 실패해도 통과로 보임**. 추가할 때 한 번 `test`로 바꿔 실행해, 의도한 이유로 실패하는지 확인함.

### 6.4 테스트가 실제로 잡는지 확인 (변조 검증)

새 테스트를 추가했다면, 대상 코드를 **일부러 한 줄 망가뜨려** 테스트가 실패하는지 확인한 뒤 원복함. 예: 권한 검사 한 줄 삭제 → 403 테스트가 실패해야 함. 통과하면 그 테스트는 아무것도 검증하지 않는 것임.

### 6.5 지켜야 할 것

- **독립성**: 테스트 순서에 의존하지 않음 (예외: `captain.spec.ts`의 `describe.serial`). 매 테스트에서 목·핸들러·localStorage를 초기화함.
- **날짜**: "오늘"에 의존하는 로직은 `now`를 고정해서 넘김. 배치는 KST 기준이므로 `new Date('2099-01-10T12:00:00+09:00')`처럼 시간대를 명시함.
- **외부 자원 금지**: 운영 DB·Azure Blob·SMTP를 호출하는 테스트를 만들지 않음. 필요하면 목으로 대체하고 "배포 후 확인 항목"으로 남김.
- **응답 노출**: 오류 응답에 내부 메시지(비밀번호, 연결 문자열 등)가 섞이지 않는지 확인함.

## 9. 문제 해결

| 증상                                                      | 원인 / 해결                                                                                                                      |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `initdb: command not found`                               | PostgreSQL 미설치 → `brew install postgresql@17`                                                                                 |
| E2E 시작 시 포트 사용 중 (54330, 3100, 4173)              | 이전 실행이 남음 → `pkill -f "e2e/.pgdata"; pkill -f "vite preview"; pkill -f "src/server.js"`                                   |
| `Executable doesn't exist … chromium`                     | 브라우저 미설치 → `npx playwright install chromium`                                                                              |
| PostgreSQL "Unix-domain socket path … too long"           | macOS 소켓 경로 103바이트 제한 → `-k /tmp/짧은경로` 지정 (E2E 스크립트는 이미 적용)                                              |
| FE 테스트 "[MSW] … unhandled request"                     | 핸들러가 없는 API 호출 → `server.use(...)`로 응답 추가                                                                           |
| Playwright "strict mode violation"                        | 같은 이름의 요소가 여러 개 → 5.5 셀렉터 규칙 참고                                                                                |
| Playwright가 45초 타임아웃                                | 숨겨진 요소를 기다리는 경우가 많음 → `.artifacts`의 스크린샷으로 화면 상태 확인                                                  |
| 캡틴 시나리오 중 한 단계만 실행하면 실패                  | `describe.serial`로 앞 단계의 모임을 이어서 씀 → `e2e/captain.spec.ts` 파일 전체로 실행                                          |
| codegen용 서버를 띄운 뒤 `test:e2e`가 시작되지 않음       | 직접 띄운 서버가 포트를 점유 → Ctrl+C로 종료 후 실행                                                                             |
| 로컬에서는 통과, 가끔 실패                                | 테스트 간 데이터 의존 또는 대기 부족 → `--repeat-each=3`으로 재현, 고정 대기(`waitForTimeout`) 대신 `expect(...)` 자동 대기 사용 |
| "Failing test passed even though it was supposed to fail" | `test.failing`의 결함이 고쳐짐 → `test`로 바꿈                                                                                   |
| BE 테스트 결과가 PC마다 다름                              | 날짜·시간대 의존 → `now`를 고정                                                                                                  |
| BE 테스트에 morgan 로그가 섞임                            | `env.js`의 morgan 목이 적용되지 않은 경우 → `jest.config.js`의 `setupFiles` 확인                                                 |
